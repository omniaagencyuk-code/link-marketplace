# Rollbacks

One file per migration that can be undone, named for the migration it
reverses. Running one leaves the database as though that migration had never
been applied.

These are not run automatically and are not part of `verify:rls`. They exist
so a feature can be backed out from the Supabase SQL editor without waiting
for someone to write the undo under pressure.

Every file says at the top what it destroys. Read that first: a rollback that
drops a table drops the rows in it, and no rollback here asks for
confirmation.

Migrations before 0019 have no rollback file. They are the marketplace
itself - websites, orders, payments - and undoing them is not a
back-this-feature-out operation but a restore-from-backup one.

| Rollback | Undoes | Destroys |
|---|---|---|
| `0019_publisher_sourcing_down.sql` | `0019_publisher_sourcing.sql` | Imported emails, unapproved drafts, extraction history, publisher cost and commercial terms. Listings already approved from drafts are ordinary listings and survive. |
| `0043_country_nobody_stated_down.sql` | `0043_country_nobody_stated.sql` | Every market the backfill established, and every one an administrator has set since. The column goes back to `not null`, so unknown has to become something: everything unknown becomes `GB` again, which is the state 0043 was written to fix. |
| `0044_country_source_down.sql` | `0044_country_source.sql` | The record of where each country came from. The countries survive, but the nightly Ahrefs refresh can no longer tell a country a person chose from one it worked out itself, and the invented United Kingdom marked `default` becomes indistinguishable from a real one. |
| `0045_refresh_one_tier_down.sql` | `0045_refresh_one_tier.sql` | Nothing. It drops the two-argument form of the due-domains selection, leaving the one-argument form from 0013. Only run it alongside application code that does not pass a tier, or every run fails its RPC call. |
| `0046_link_monitoring_down.sql` | `0046_link_monitoring.sql` | Every monitoring row: which links were checked, which were lost and when, and every guarantee claim with the amount it was opened for. The durability scores go with them and cannot be recomputed afterwards. Take a dump of the three tables first if any claim has ever been opened. |
| `0047_promo_codes_down.sql` | `0047_promo_codes.sql` | Every promo code and every redemption of one. Orders keep the amount taken off them only until the three columns go with it, after which a discounted order reads as though it was sold at a price nobody charged. Stripe coupons are left alone - archive them in the Stripe dashboard if you want them gone. |
| `0048_description_runs_down.sql` | `0048_description_runs.sql` | The record of which description sweeps have run, and of which listings have already been read. The descriptions themselves survive. Losing the read record means the next sweep works through the whole inventory again, including the homepages already known to carry nothing usable. |
| `0049_stamp_without_touching_updated_at_down.sql` | `0049_stamp_without_touching_updated_at.sql` | Nothing. It restores the blanket `updated_at` trigger from 0001. Only run it alongside code that does not run a description sweep: with the sweep in place the blanket trigger resets the last-edited date on every listing it reads, and those dates cannot be recovered. |
| `0050_organic_keywords_down.sql` | `0050_organic_keywords.sql` | The keyword count on every listing. Cheap to lose - the next refresh collects it again for free - but every listing reads as unmeasured until that refresh reaches it, up to a month on tier 3. Only run it alongside code that does not select `org_keywords`, or the refresh update fails and takes domain rating and traffic with it. |
| `0051_refresh_stamp_is_not_an_edit_down.sql` | `0051_refresh_stamp_is_not_an_edit.sql` | Nothing. It returns the trigger to the 0049 version. Do not run a metric backfill while it is in that state: clearing `last_ahrefs_refresh_at` across the inventory then resets the last-edited date on every listing, and those dates cannot be recovered. |
| `0052_tier_preview_down.sql` | `0052_tier_preview.sql` | Nothing. It drops a read-only function; no tier is changed by dropping it, because 0052 never wrote one. Only run it alongside code that does not call `ahrefs_tier_preview`, or the Assign tiers button fails on its preview before assigning anything - and the refusal that stops a cadence the budget cannot meet goes with it. |
| `0053_sales_centre_down.sql` | `0053_sales_centre.sql` | The whole Sales Centre: prospects, crawled pages, qualifications, contacts found with Hunter credits, campaigns, every email drafted or sent, replies, the timeline, and the Hunter credit ledger the budget is counted from. Two cannot be rebuilt: `sales_suppressions` is the do-not-contact list, and dropping it also removes the trigger that makes an unsubscribe binding - export it somewhere that survives before running this. `prospect_attributions` records which outreach produced which customer and is written once on purpose, so nothing can recompute it. Orders, customers and the marketplace are untouched. |
| `0054_link_gap_down.sql` | `0054_link_gap.sql` | Every gap report customers have run and its results, the cached referring-domain pulls, and the ledger of what Ahrefs charged. The cache is the expensive loss: those pulls cost units, and dropping them means buying each domain again at full price - export `refdomain_snapshots` first. Dropping the ledger mid-cycle resets the feature's measured spend to zero, so re-applying 0054 in the same cycle can spend the allowance twice. The refresh's budget, ledger and settings are separate tables and are untouched, which is the point of them being separate. |
| `0055_gap_projects_down.sql` | `0055_gap_projects.sql` | Every saved site a customer has set up: the client name, the domain, the competitors somebody chose and the market. Nothing can recompute a choice, so export `gap_projects` first. The cached competitor lookups go too, at fifty units a domain to buy back. Reports and their results survive, but a report stops knowing which saved site it came from, and the ledger stops being able to tell a fifty-unit suggestion from a 2,500-unit referring-domain pull - the sum is unaffected, so the budget still reads correctly. Only run it alongside code that does not select `project_id` or write `kind`, or saving a site and suggesting competitors both fail. |
| `0056_gap_sellable_needs_a_price_down.sql` | `0056_gap_sellable_needs_a_price.sql` | Nothing. It restores the 0054 `gap_sellable`, which counts any active listing as sellable whether or not anything on it can be bought - so a report again offers sites under "available here" that carry no orderable service, and the results table shows that claim above a row with no Add to order button. Reports already run are untouched either way: the function decides what a future report counts, not what a stored one holds. Only run it alongside code from before the expandable results table. |
| `0057_publisher_inbox_counts_in_sql_down.sql` | `0057_publisher_inbox_counts_in_sql.sql` | Nothing. It drops two read-only functions and an index. The publisher inbox goes back to what 0057 fixed: the duplicate finder reads every pending and approved draft with its jsonb and a join, ten round trips, growing with every approval; and the status tiles count a thousand-row capped read, so they describe whichever thousand emails came back rather than the inbox. Only run it alongside code from before 0057, which does that work in JavaScript - with the current code the tiles read zero and the duplicates card reads empty. |
| `0058_approve_all_confident_drafts_down.sql` | `0058_approve_all_confident_drafts.sql` | The record of which approve-all runs happened, who started them and what they approved. The listings those runs created are untouched - `draft-approval.ts` wrote them, not this - and the drafts keep their approved status. The eligibility rules go with the functions, but `bulkApproveConfidentAction` keeps its own copy, so the hundred-at-a-time path through the browser still works; only the background run stops. Remove `/api/cron/draft-approvals` from vercel.json at the same time, or the cron ticks every five minutes against a missing function. |
| `0059_approve_everything_priced_down.sql` | `0059_approve_everything_priced.sql` | The record of which rule each approve-all run used and whether it applied the general price to unmentioned niches. The runs and the listings they created survive; what is lost is the distinction between "approved as confident" and "approved under the priced rule with niches spread" - the more consequential of the two, and not reconstructable from the listings. Export `draft_approval_runs` first if that ever has to be defended. The eligibility functions return to strict-only, which against a real backlog matched 17 drafts out of 7,204. Only run it alongside 0058-era code: the current code passes a mode argument, so with this applied an approve-all fails outright rather than quietly approving the wrong set. |
| `0060_priced_means_any_price_down.sql` | `0060_priced_means_any_price.sql` | Nothing, but it reinstates a bug. The priced rule narrows back to `guest_post_cost` alone, so a publisher who quoted a price for writing the article themselves, or who only sells link insertions, stops being approvable in bulk - against a real backlog that was the difference between 1,132 drafts and several thousand. Nothing already approved is affected. There is no version of this that is correct and this one is not. |
| `0061_relationship_is_not_a_different_site_down.sql` | `0061_relationship_is_not_a_different_site.sql` | Nothing, but it reinstates a bug that stopped the whole queue. It puts `different-site-offered` back in the bulk exclusion list; that flag is set on any non-empty `relationship`, and against a real backlog it fired on 7,304 drafts out of 7,307 ("owner", "Site from the publisher's rate card", "Agency/reseller offering guest posts"), so the priced rule goes back to offering nothing at all. The exclusion assumed approving would write one site's terms against another's row; the extraction rule says the offered site IS the listing, so there was never a mismatch to catch. |
| `0062_blocked_senders_down.sql` | `0062_blocked_senders.sql` | The list of senders we refuse to buy from, and why each was added. The replies themselves are untouched and no listing was ever changed by a block - but every address on that list was somebody a person decided against, usually for quoting several times what four other sellers quote for the same site, and there is no recovering who they were. The replies they sent come back as unread, so the next extraction run pays to read all of them again. Export `sourcing_blocklist` first if the blocks are to survive. Replies silenced by a block keep `status_reason = 'Sender blocked'`, so they can be found and reset by hand; the file says how. |
| `0063_price_services_in_one_statement_down.sql` | `0063_price_services_in_one_statement.sql` | Nothing - no price changes and no row is removed. What it costs is the recalculation: service prices go back to one `UPDATE` per row, ten at a time, which against 4,954 services is 496 sequential round trips and about fifty seconds before the niche prices are even started. That is what timed the admin screen out and left 3,479 services on the new rules and 1,475 on the old. Only run it alongside 0062-era code; current code calls the function and a recalculation fails outright without it, which is the safer failure - it stops rather than half-pricing the marketplace. |
| `0064_marketplace_search_in_sql_down.sql` | `0064_marketplace_search_in_sql.sql` | Nothing - no table, column or row; it drops a view and a function that only read. Only run it alongside 0063-era code: the current marketplace calls `marketplace_search` and fails outright without it, which is the safer failure - it stops rather than quietly showing buyers a different set of publishers than the filters claim. |
| `0065_marketplace_facets_down.sql` | `0065_marketplace_facets.sql` | Nothing - one function that only counts. The cost is the sidebar: the marketplace no longer holds the inventory so it cannot count it, and without this the niche counts, the language list and the country list have no source. The page fails rather than quietly offering filters that match nothing. Drop it only alongside 0064's rollback and 0063-era code, which still filters in the browser and counts there too. |
| `0066_publish_the_backlog_down.sql` | `0066_publish_the_backlog.sql` | The record of which publish runs happened, who started them and what they published.
